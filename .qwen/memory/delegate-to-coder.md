# Как делегировать coder'у (актуально 15.11.2026)

Основание: 13.11 coder 4 раза не выполнил задачу из-за общих промтов. Вывод: промт должен
быть конкретным. С 15.11 coder реализует ВСЕ файлы плана (включая boot.S/linker.ld) —
с guardrails; коммит делает оркестратор после /board (в шаблоне шага коммита НЕТ).

## Шаблон промта

Ты — coder. Задача: [цель]. Файлы плана: [список путей от корня репо].
НЕ ТРОГАТЬ: [список]. Лимит: ~30% изменений файла. Удаления — только по пункту плана.

## ШАГ 1..N: правки
Путь: [относительный путь]. Найти: [фрагмент]. Заменить: [фрагмент].
(Новый файл — полное содержимое. Регистры — только architecture.md/datasheet.)

## ШАГ N+1: сборка
make clean && make && make check
Ожидание: без ошибок; «OK: entry == 0x8000», «OK: vectors < 0x100».

## ШАГ N+2: QEMU
make qemu-log
Ожидание (дословно): [строки из плана; базово «RESULT: PASS», 12 passed/1 skipped —
ATAG SKIP в QEMU норма; alive irq==ticks spurious=0].

## ШАГ N+3: отчёт (≤30 строк)
git diff --stat; дословный хвост build/uart.log; 3 пункта что/зачем;
что человеку проверить на плате (ожидаемый UART, LED).

## Ограничения
- 3 неудачи сборки/теста → [ESCALATE] с логом, не повторять по кругу.
- Запрещено: git commit/push, sudo, дисковые команды, выдуманные адреса, файлы вне плана,
  QWEN.md и .qwen/agents|commands, .qwen/memory, попутные рефакторинги.
- Зависимости от заголовков в makefile ЕСТЬ (-MMD -MP); clean-сборка всё равно обязательна.

## Когда звать debugger вместо coder
Архитектурные решения, анализ чужого кода, противоречие плана коду, 2 круга без успеха.
