# Контекст проекта для агента — Enclave OS

Файл для агентской памяти: что здесь происходит, что нельзя ломать, как проверять
и что дальше. Дневник обучения — в `README.md`, здесь только рабочее состояние и
правила. Язык кода и комментариев в проекте — русский, отступы — 4 пробела (в
`makefile` — табы, см. ниже).

## Что это

Голое ядро для **Raspberry Pi 1 Model B+** (SoC BCM2835, CPU ARM1176JZF-S,
ARMv6, 512 МБ ОЗУ), без libc и без загрузчика. Долгосрочная цель — Enclave OS:
изоляция пользовательских «анклавов» через режимы CPU, MMU, таблицы страниц,
SVC-шлюз и guard pages.

Сейчас реализован только bootstrap: векторы, стеки всех режимов, очистка BSS,
драйвер UART, вечный цикл после печати.

## Файлы

| Файл | Назначение |
|---|---|
| `boot.S` | точка входа `_start`: стеки режимов, копирка векторов на 0x0, BSS, проброс `r0`/`r1`/`r2` в `kernel_main`, таблица векторов, макрос `EXC_HANDLER` (кадр + паника либо возврат из пробы) |
| `kernel_main.c` | `uart_init`, отчёт в UART + selftest с вердиктом PASS/FAIL, `panic(tag, frame)` с дампом, пробные исключения |
| `uart.c` / `uart.h` | минимальный драйвер PL011 (115200 8N1) |
| `linker.ld` | раскладка с `. = 0x8000`, символы `__bss_start/__bss_end/__kernel_end` |
| `makefile` | сборка + цели `run`/`debug`/`check`/`size`/`disasm`/`symbols`/`sections` |

## Окружение

`arm-none-eabi-gcc` 14.2.1 и `qemu-system-arm` 10.0.13 (машины `raspi0`,
`raspi1ap`, `raspi2b`). Пакеты ставит пользователь, агент — нет. Сборку и прогон
в QEMU агент выполняет сам и показывает вывод.

Git: локальная подпись `My_Ai <semen.trololo@ya.ru>` (только этот репозиторий),
совместная ветка — `My_Ai`. `git add -A` не использовать, стейдж точечный
(иначе в историю попадут артефакты; `build/` скрыт `.gitignore`). Push — только
по прямой просьбе.

## Текущее состояние (проверено 2026-11-11)

```
make rebuild   → exit 0, 0 warning, 0 error
make check     → OK, _start на 0x8000
make run       → отчёт + selftest, "RESULT: PASS" (7 проверок)
kernel.img     → тот же отчёт под QEMU через -device loader (замер 11.11.2026)
M1 (дампы)     → udf и svc дают дамп, pc совпадает с адресом инструкции
git            → ветка My_Ai: M1 + selftest + QWEN.md закоммичены 11.11.2026
```

Самопроверка живёт в **основном** образе: отдельная тестовая сборка для неё не
нужна, на плате других глаз, кроме UART, не будет (задел под M7.5 — M0/M1 уже
накрываются PASS/FAIL). `-DTEST_UND`/`-DTEST_SVC` оставлены только для
принудительной паники: она останавливает ядро и в вердикт не влезает.

Проверяемые сейчас пункты: id CPU (part 0xB76), обнуление `.bss`, копирка
векторов в 0x0 (пословно + инвариант размера), стек SVC, поимка `udf` и `svc` с
возвратом, сохранность `r0`–`r12` сквозь исключение. Проба исключения заодно
доказывает, что таблица в low memory работает: на ARMv6 нет VBAR, CPU гарантированно
берёт вектор с 0x00.

Размеры: `text 4041`, `data 0`, `bss 81972` байт. Раскладка:

```
0x8000  _start / .text.boot
0x80e8  _vectors_start        0x8124  _vectors_end      (блок копировки = 60 байт)
0x8124  шесть обработчиков исключений: undef/svc/pabt/dabt/irq/fiq
0x8618  __bss_start
        irq → 0x9618, fiq → 0xa618, abt → 0xb618, und → 0xc618 (по 4 КБ)
        svc → 0x1cfd0 (64 КБ), дальше exc_caught/exc_pc/exc_probe = __kernel_end
```

Стек User/System **не** инициализирован намеренно: его назначает ядро при входе в
анклав. `exc_*` объявлены в `kernel_main.c` **не static** — их трогает ассемблер
по абсолютным адресам.

### Что печатает ядро (эталон для сверки с платой)

```
Enclave OS boot
BCM2835 / ARM1176JZF-S - boot report
--- INFO ---
  cpu id        0x410fb767        на плате обязан совпасть — это ARM1176
  cp15 ctrl     0x00050078        состояние MMU/кэшей на входе: сверить с платой
  cpsr         0x600001d3         SVC, I/F замаскированы
  sp / svc stack top / vectors src / vectors size 0x3c
  boot r0 / boot r1 mach / boot r2 atags       как их принёс firmware
  atag @0x100 / atag id@0x104 + вывод atags / atags path
--- CHECKS ---
[PASS] cpu part number is ARM1176 (0xb76)
[PASS] bss zeroed by boot.S
[PASS] vector table lives at 0x00000000
[PASS] svc stack is the one boot.S set up
[PASS] undef instruction trapped and resumed
[PASS] svc trapped and resumed
[PASS] r0-r12 survive an exception
--- RESULT ---
selftest: 7 passed, 0 failed
RESULT: PASS
```

Отличия на плате, которые видно прямо из этого вывода: `boot r1 mach` и
`boot r2 atags` перестанут быть нулями, `atag id@0x104` станет `0x54410001`,
`atags path` переключится на `via r2`. Строки отчёта — строго ASCII: на
последовательном терминале кодирование может быть любым.


## Инварианты — нарушать нельзя

1. **Размер блока векторов < 0x100.** Копируется отрезок
   `[_vectors_start, _vectors_end)` целиком по адресу 0x0; по 0x100 лежат
   ATAGS/DTB. Сейчас 60 байт (0x00…0x3B). Любая правка таблицы или добавление
   данных в `.text.boot` до `_vectors_end` обязана сохранять запас.
   Проверка: `arm-none-eabi-nm build/kernel.elf | grep _vectors_`.
2. **Обработчики — строго после `_vectors_end`**, иначе их тоже скопирует на 0x0.
   Про «±4 КБ»: ограничение относится не к обработчикам, а к **пулу литер** —
   `ldr pc, =…` читает адрес из `.ltorg`, и пул обязан лежать в 4 КБ от
   инструкции. Сам адрес в пуле абсолютный, так что обработчик может стоять
   далеко (после M1 они как раз разъехались).
3. **Возврат из исключения — только `subs pc, lr, #N`**, не `bx lr`. Обработчики
   M1 прерывания маскируют и в `panic` не возвращаются — это осознанно:
   исключение должно быть заметным, а не тихо возвратом в неизвестность.
   Возврат появится вместе с контекстом анклава (M6).
4. **Ни одной инструкции со стеком до инициализации SP** в `_start`.
5. **Регистры периферии — только `volatile`** (иначе `-O2` съест доступы).
6. **Прототипы C — в заголовке.** GCC ≥ 14 считает implicit declaration ошибкой.
7. **Рецепты `makefile` — с таба**, не с пробелов: иначе `*** пропущен
   разделитель` и `make` не запускается вообще (на этом проект уже стоял).
8. **Ядро грузится на 0x8000**, low memory (0x0…0x7FFF) зарезервирована.

## Известные риски и долг

- **ELF затирает low memory в QEMU.** Единственный `PT_LOAD` имеет
  `VirtAddr = 0x00000000` (линкер выровнял сегмент вниз по 0x10000), поэтому
  `-kernel kernel.elf` грузит ELF-заголовки в 0x0. Сейчас безвредно: векторы мы
  сами копируем поверх, и `check_vectors_copied()` проходит. `-Ttext-segment=0x8000`
  НЕ помогает. **Проверенное лечение (замер 11.11.2026):** `-z max-page-size=0x1000`
  в `LDFLAGS` → `LOAD VirtAddr = 0x00008000`, low memory чиста. В makefile НЕ
  добавлено по решению пользователя (11.11.2026: «расхождения эмулятора будем
  решать перед тестом на реальном железе, на мелочь не обращать внимание»).
  Ручная проверка лечения:
  `arm-none-eabi-ld -T linker.ld -nostdlib -z max-page-size=0x1000 build/*.o -o /tmp/small.elf`
- **QEMU raspi1ap вообще не пишет ATAGS** — ни с `-kernel kernel.elf`, ни с
  `-kernel kernel.img` (переснято 11.11.2026 на QEMU 10.0.13; более ранняя запись
  про «с `.img` теги на месте» была неверной). Разбор ATAGS в QEMU придётся
  **подсовывать**: `-device loader,file=atags.bin,addr=0x100,force-raw=on`
  работает вместе с `-kernel kernel.elf` (проверено: ядро читает подставленный
  список). Важный подвох: `-device loader` с `addr=` перехватывает точку входа,
  поэтому **два loader подряд ядро глушат** — loader обязан быть один, а ядро
  приходить через `-kernel`.
- **`-kernel build/kernel.img` в QEMU не запускается:** сырой образ не ложится на
  0x8000 (замер: по 0x8000 нули), ядро молчит. Board-подобный прогон только так:
  `-device loader,file=build/kernel.img,addr=0x8000,force-raw=on`.
- **Порядок слов в ATAG-списке** легко прочесть неправильно: по самому адресу
  лежит `size` тега (для ATAG_CORE = 5), а `0x54410001` — следующим словом.
  Отчёт печатает оба, чтобы не гадать.
- `-Werror` в `CFLAGS` не включён: предупреждений сейчас ноль, включать решаем
  отдельно.
- `uart.c` использует `asm` — сломается при `-std=c23`/`-std=c17` (дефолт GCC 14 —
  `gnu23`, где всё компилируется).
- В `.bss` нет явного `(NOLOAD)` — работает, потому что входные секции NOBITS.
- CI нет; проверка — сборка + selftest в UART.

## Как проверять

```bash
make -n run                                   # синтаксис makefile без сборки
make clean && make                            # сборка с нуля
make check                                    # _start на 0x8000
make run                                      # Ctrl+C для выхода: ядро в while(1)
```

Особенности проверки, на которые уже наступали:

- `make run` надо запускать в **настоящем терминале**. При перенаправлении stdout
  в pipe/файл вывод `-serial stdio` теряется в буфере — кажется, что ядро молчит.
- Автопроверка вывода: `-serial file:/tmp/ser.txt`, затем `cat /tmp/ser.txt`.
- `timeout` к QEMU — только с `-s INT`; на голый SIGTERM лог `-d in_asm` не
  сбрасывается и выглядит пустым при живом ядре.
- Состояние CPU — монитором: `-monitor stdio -S` с `-serial null` (stdio занят),
  команды `info registers`, `xp /8x 0x0`, `cont`, `stop`.

### Три прогона, которые надо различать

| Зачем | Команда | Что доказывает |
|---|---|---|
| Быстрый | `make run` | ELF грузится, отчёт и `RESULT: PASS` идут в UART. Ctrl+C для выхода |
| Как на плате | `qemu-system-arm -M raspi1ap -device loader,file=build/kernel.img,addr=0x8000,force-raw=on -display none -serial stdio -no-reboot` | ровно тот `kernel.img`, что поедет на SD-карту, печатает тот же отчёт |
| Репетиция M2 | `qemu-system-arm -M raspi1ap -kernel build/kernel.elf -device loader,file=/tmp/tb/atags.bin,addr=0x100,force-raw=on -display none -serial stdio -no-reboot` | ядро видит ATAG-список: `atag id@0x104 0x54410001`, `atags : ATAG_CORE present` |

Замер ATAGS-слов до старта — монитором: `-S` + `xp /2x 0x100`. Слово по 0x100 —
это `size` тега (5), номер тега лежит по 0x104.

`atags.bin` для третьего прогона:

```bash
python3 -c "
import struct
core = struct.pack('<IIIII', 5, 0x54410001, 1, 0, 0)   # ATAG_CORE
mem  = struct.pack('<IIII', 4, 0x54410002, 512*1024*1024, 0)
open('/tmp/tb/atags.bin','wb').write(core + mem + struct.pack('<II', 0, 0))"
```

### Дамп исключения (путь паники)

Сами исключения уже покрываются selftest в основном образе. Отдельная сборка
нужна только чтобы увидеть **дамп паники**: она останавливает ядро, в вердикт
её вписать нельзя. Флаги `-DTEST_UND` (`udf #0`) и `-DTEST_SVC` (`svc #0`); цели
в makefile нет, и `make 'CFLAGS+=…'` флаг не добавляет (`CFLAGS` объявлен через
`:=`), поэтому образ собирается вручную теми же командами:

```bash
mkdir -p /tmp/tb
arm-none-eabi-gcc -mcpu=arm1176jzf-s -marm -ffreestanding -nostdlib \
    -mfloat-abi=soft -Wall -Wextra -O2 -DTEST_UND -c kernel_main.c -o /tmp/tb/km.o
arm-none-eabi-ld -T linker.ld -nostdlib build/boot.o /tmp/tb/km.o build/uart.o \
    -o /tmp/tb/test_und.elf
arm-none-eabi-objdump -d /tmp/tb/test_und.elf | grep -m1 -B1 udf    # ожидаемый pc
timeout -s INT 6 qemu-system-arm -M raspi1ap -kernel /tmp/tb/test_und.elf \
    -display none -serial file:/tmp/d.txt -no-reboot; cat /tmp/d.txt
```

Критерий: `pc` в дампе обязан равняться адресу инструкции из `objdump`, `lr` —
ему + 4. Пройденный эталон (2026-11-11): `udf #0` на `0x8928` →
`pc = 0x00008928`, `lr = 0x0000892c`, `spsr = 0x600001d3`. Сам дамп печатается
**после** полного отчёта selftest — все 7 проверок видны и перед паникой.

Два независимых переключателя, их часто путают:

- **что печатается** — зависит от флага компиляции. `make run` зависит от `$(ELF)`,
  то есть всегда гоняет `build/kernel.elf` **без** `-DTEST_*`: там полный отчёт и
  вердикт, но дамп паники не появится, и это правильно. Тестовый образ —
  отдельный файл, make о нём не знает;
- **куда девается UART** — ключ QEMU: `-serial stdio` в терминал (смотреть
  глазами, висит до Ctrl+C), `-serial file:` в файл (для автосверки; в pipe
  вывод не ловить — буферизация), `-serial null` когда занят монитором.

## План: минимум до железа

Цель — **запустить и обкатать ОС на реальной Raspberry Pi 1 Model B+**. Правило
игры: веха не считается закрытой, если её нельзя проверить тем же самым
`kernel.img` на плате. Поэтому предпоследняя веха — selftest, а не «красивый
лог»: на плате нет ни монитора, ни gdb, ядро должно само печатать вердикты.

| # | Веха | Готово, когда (проверка в QEMU) |
|---|---|---|
| M0 | Bootstrap | ✅ 2442a0d — `Enclave OS boot`, 0 warning |
| M1 | Реальные обработчики исключений: сохранить `r0`–`lr`, `SPSR`/`LR_<mode>`, `panic(tag)` с тегом и PC вместо `b`-на-себя | ✅ 2026-11-11 — `udf`/`svc` дают дамп с корректным PC, блок векторов остался 60 байт |
| M2 | Проброс настоящих `r0`/`r1`/`r2` + разбор ATAGS/DTB (детали ниже) | распечатаны machine type и все теги; путь получения списка (регистр или fallback) напечатан явно |
| M3 | Прерывания: контроллер BCM2835 (база `0x2000B200`, линия PL011 = 57), снятие источника, `CPSR.I` | символ эхом возвращается по прерыванию, поллинга в пути нет, на 115200 потерь нет |
| M4 | Тик планировщика: BCM2835 System Timer (база `0x20003000`), compare-канал по IRQ | счётчик тиков монотонно растёт (1 МГц по datasheet — сверить), тик 1 Гц печатается |
| M5 | MMU, section-таблицы 1 МБ: векторы RO для ядра, периферия device/nGnRE, стек анклава + guard page | печать идёт с включённым MMU; чтение guard page → Data Abort с корректным DFAR; чтение ядра из user → abort |
| M6 | SVC-шлюз (вектор 0x08) + вход в User mode + `struct enclave_ctx` (SP_usr, банк регистров, таблицы) | анклав печатает через SVC; прямая запись в UART из User → Data Abort; SVC заведомо неверными аргументами отбит без падения ядра |
| M7 | Round-robin на 2 анклава по тику | два анклава чередуются; падение одного не роняет ядро и не глушит второй |
| M7.5 | **Selftest одним бинарником**: проверки M1–M7 печатают таблицу `PASS/FAIL` | тот же `kernel.img` даёт построчно одинаковый вывод в QEMU и на плате |
| M8 | Запуск на Pi 1 B+ | та же таблица PASS по настоящему UART |

Смысл M7.5: отлаживать плату без автотеста — значит перегонять SD-карту ради
каждой строки. С selftest QEMU становится настоящим предварительным прогоном, а
не имитацией. **Каркас уже работает с 2026-11-11** (7 проверок M0/M1 в основном
образе, `RESULT: PASS`) — дальше к нему только добавляем проверки закрытых
вех, а не пишем инфраструктуру в конце. Цель `make selftest` специально
убрана из формулировки: makefile не трогаем, проверка и так живёт в `make run`.

### Подготовка к M2

1. **Проброс `r0`/`r1`/`r2` — сделано 2026-11-11.** `boot.S` больше не подставляет
   machine type константой: `_start` сохраняет `r1` в `r5` (раньше терялся — в
   `r4` доезжал только `r2`), вызов собран как `mov r1, r5`. Отчёт печатает все
   три регистра как есть, так что на плате видно фактическое значение machine
   type вместо красивой константы. В `README.md` строка «R1 = 0xC42» — непроверенное
   утверждение из прошлых записей, на плате сверим по строке `boot r1 mach`.
2. **QEMU не даёт ни `r2`, ни тегов** (переснято 11.11.2026, QEMU 10.0.13):
   `R0=R1=R2=0` и по 0x100 тоже пусто — ни с ELF, ни с `.img`. Раньше здесь было
   записано обратное («с `.img` теги лежат»), это не так. Парсер обязан: брать
   `r2`, если по нему читается ATAG_CORE, иначе fallback на 0x100, и **печатать,
   каким путём пошли** — эта ветка уже живёт в `atags_report()`. Репетиция в
   QEMU — инжекция списка через `-device loader` (см. «Как проверять»).
3. **Риск ELF (`PT_LOAD` с `VirtAddr = 0`) не закрыт по решению пользователя** —
   лечится одной опцией линкера, но решается перед выходом на железо. Для M2 в
   QEMU это не блокер: теги всё равно подсовываются loader'ом.

### Расхождения QEMU ↔ Pi 1 B+ (сверять на каждой вехе)

| Что | QEMU `raspi1ap` | Реальная плата |
|---|---|---|
| Загрузка | `-kernel` ELF; сырой `.img` через `-kernel` **не стартует** (не ложится на 0x8000) — нужен `-device loader` | только `kernel.img` через `start.elf`, всегда на 0x8000 |
| `r0`/`r1`/`r2` | нули (замерено) | их заполняет firmware |
| ATAGS по 0x100 | **нет ни при какой загрузке** (замер 10.0.13); подсовывать вручную | есть всегда |
| Разметка ATAG | слово `size` по 0x100, номер тега по 0x104 | так же |
| Такт UART | модель игнорирует делители | 3 МГц, `IBRD`/`FBRD` критичны |
| System Timer | моделируется | реальные 1 МГц |
| Паника | можно остановить монитором | только вечный цикл + гашение прерываний; watchdog сам не трогаем |
| Отладка | монитор, gdb через `-s` | только то, что ядро напечатало в UART |

Из этого списка на результат selftest в QEMU влияет только ATAGS — поэтому
`atags`/`atags path` напечатаны как факт, а не как PASS/FAIL: в эмуляторе «тегов
нет» не является ошибкой. Остальные расхождения вскрываются на плате теми же
строками отчёта.

### M8: что нужно для запуска на плате

- **SD**: FAT32 с MBR, в корне `bootcode.bin`, `start.elf`, `fixup.dat` (из
  `raspberrypi/firmware`, версия с поддержкой Pi 1), `config.txt`, `kernel.img`.
- **`config.txt` минимум**: `kernel=kernel.img`; `disable_overscan=1` (если
  смотрим HDMI); `uart_2ndstage=1` на время отладки загрузки. Не ставить
  `kernel_old=1` (иначе загрузит в 0x0) и не отключать `disable_commandline_tags`
  — без ATAGS встанет M2.
- **Консоль**: USB-TTL **строго 3.3 В** (GPIO не 5-вольтовые): TX адаптера →
  GPIO15, RX адаптера ← GPIO14, GND общий, 115200 8N1. Наш `uart_init` уже
  переключает 14/15 в alt0, так что софтовая часть готова.
- **Признак жизни при полной тишине**: активность светодиода платы/SD — значит
  GPU загрузился и дело в ногах/скорости; тишина LED — проблема на этапе
  `bootcode.bin`/`start.elf`, ядро вообще не запускалось.
- Сборка для платы — **`kernel.img`**, не ELF. В QEMU он уже гоняется тем же
  содержимым через `-device loader` (см. «Как проверять»), так что расхождение
  «ELF в QEMU / `.img` на плате» закрыт проверкой образа, а не правкой makefile.

Порядок M1→M8 не стоит менять: без обработчиков невозможна отладка M2–M4, без
MMU невозможны M5–M7, а анклав без guard page — это не анклав.
